A technical support lab run like production: audited, hardened, and tested from the outside.

Multiple Proxmox nodes, 28 containers, a virtualized firewall, and no inbound ports for administration. In September 2026 I audited it as if it were someone else's environment, fixed what I found, and proved each fix from the side a failure or an attacker would come from.

Architecture

Multi-node, one flat LAN, three outbound overlays

The edge host runs the firewall and DNS, so the network stays up while the main host is down for maintenance. Everything I reach remotely comes in through connections that dial out, so the firewall has no inbound rules for administration at all.

Method

The same loop I'd run on a customer's problem

Support work and infrastructure work share one habit: don't trust that something is fixed until you've watched it fail safely.

1

Inspect

Read the live systems: every guest config, every listening port, the firewall export.

2

Audit

Read it back as a stranger and rank what I found by risk.

3

Check first

Prove nothing depends on a thing before I remove it.

4

Fix, then prove

Test from outside: another host, a phone on cellular, a forced failure.

5

Write it down

Document the result and add a runbook so it can be repeated.

Seven fixes, each with before, after and proof

04 · OPNSENSE✓ verified

The VPN kill switch that wasn't

A few hosts are policy-routed through a WireGuard tunnel to a VPN provider, with a block rule underneath as a kill switch. On paper, if the tunnel drops, their traffic stops.

It didn't. With the gateway down, the policy rule still matched and sent the traffic out the regular WAN. The block rule never got a chance to act. The fix is one setting, "Skip rules when gateway is down". Finding the cause took longer than fixing it.

  • Tunnel down: routed host still reaches the internet through the ISP. Leak.
  • Config backed up; "Skip rules when gateway is down" enabled (OPNsense 25.7).
  • Gateway forced down: curl to two IP-echo services times out, ICMP 100% loss.
  • LAN access and non-VPN hosts unaffected.
  • Gateway restored: host exits through the VPN provider again.
01 · BACKUPS✓ restore-tested

Encrypted backups of what can't be replaced

BeforeNo scheduled backups of Vaultwarden, Authentik, Infisical or cloudflared.
AfterDaily application-level dumps and snapshots, checked, then age-encrypted to a key kept off the host. 7 daily and 4 weekly runs kept.
ProofRestored on a separate machine: every file decrypted, every SHA-256 matched.
02 · DOCKER✓ verified

An open Docker API, closed

BeforeEngine API on tcp/2375, no authentication, on two containers: a host takeover from anywhere on the LAN.
AfterAfter a config search on both nodes and a ten-minute live connection watch found no consumers, the TCP listener was removed.
ProofFrom another host: nc refused, nmap closed. Local socket fine; Authentik healthy in ~25 s.
03 · POWER✓ dry-run tested

UPS that actually shuts things down

BeforeUPS units on USB with nothing watching them.
AfterNUT on both nodes: stop every guest cleanly, then halt. The smaller UPS triggers early (180 s or 50%) to leave headroom.
Proofupsc reporting on both, upsdrvctl -t shutdown, hook dry run. The real forced shutdown was deliberately not fired.
05 · TAILSCALE✓ verified

Subnet router with split DNS

AfterPersistent forwarding, LAN route approved, internal domain resolved by AdGuard Home over the tailnet.
SnagA laptop on the LAN began sending its local traffic through the tailnet. Fixed with a NetworkManager routing rule on the home Wi-Fi only.
ProofFrom an iPhone on cellular, a LAN-only service loaded by internal hostname.
06 · TAILSCALE✓ tests pass

An ACL that tests itself

BeforeDefault allow-all.
Aftertag:router; LAN reachable only on 53, 80, 443, 8006; autoApprovers for route and exit node. Built-in tests allow DNS, web and the Proxmox UI, and deny SSH, the Authentik admin port and the Docker API.
ProofFrom cellular, SSH to a LAN host times out, and the same port answers from inside the LAN.
07 · TAILSCALE✓ verified

Exit node, no IPv6 leak

AfterRouter advertises an exit node, approved automatically by policy.
ProofIP-echo shows the home WAN with it on and the carrier with it off. No IPv6 default route on the router, so no leak over the carrier's IPv6.
Remote access

Three overlays, one job each

Running all three side by side is deliberate: each solves a different problem, and comparing them is the fastest way to understand what each one is really doing.

ToolUsed forWhy this one
TailscaleReaching the LAN from my own devices, anywhereDevice-to-device with NAT traversal; one subnet router instead of a client in every container
TwingateAccess to specific services for specific identitiesResource-level policy without exposing a subnet; a useful contrast with Tailscale ACLs
Cloudflare TunnelPublic web ingress for two servicesOutbound-only connector, TLS and DDoS handled upstream, no port forward

Known limitation, written down rather than hidden: the LAN uses the most common home /24, so it can collide with a remote network's range. The options are renumbering the LAN or using 4via6. remote-access.md ↗
